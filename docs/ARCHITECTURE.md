# Architecture

```text
 CLI (zk-cli)            Browser (web/ -> Worker -> zk-wasm)
        \                   /
         zk_sdk::portable  (bytes in, bytes out, size-bounded)
                 |
            Zk facade  (compile, setup, prove, verify, verify_batch, inspect)
                 |
   zk-core (policy, formats, KeyBinding)   zk-witness (R1CS + sym -> .wtns)
                 |
        zk-spartan-whir  ->  upstream spartan-whir (pinned), KoalaBear, Poseidon
```

- `zk-core` knows nothing about a specific backend. `Backend` is the only seam.
- Keys and proofs carry a `KeyBinding {backend, backend_version, policy, program_id, vk_id}`. `vk_id` is a domain-separated SHA-256 over those fields and the verifying-key bytes. Decoding re-derives it, so tampered or foreign keys fail before any cryptography runs.
- Artifacts are framed (`ZKSDK002` magic, format version 2, length-prefixed, hard size limits). Backends use bounded bincode, fixed-int little-endian.
- Verification always calls the upstream verifier after `verifying_key.authenticate()`; the expected public inputs are supplied by the caller, never read from the proof.
- File I/O (`zk_sdk::files`) is compiled out on wasm32. Randomness on wasm comes from the browser CSPRNG through `getrandom`'s `wasm_js` backend; there is no fallback.
- Native builds enable upstream `parallel` (rayon). The default `zk` is portable x86-64; `scripts/build_optimized.py` adds an AVX2/BMI2 `zk-avx2` beside it, and the portable `zk` hands each invocation to it when the CPU supports both (`ZK_PORTABLE=1` opts out; `crates/zk-cli/src/dispatch.rs`). Library users choose with `RUSTFLAGS=-C target-cpu=...`.
- The browser has two bundles: `web/pkg` (single-threaded, any page) and `web/pkg-threads` (rayon over Web Workers on shared memory, built with a pinned nightly and a rebuilt std). `web/worker.js` loads the threaded one only on a cross-origin-isolated page. Proofs are interchangeable across every configuration: the code and parameters are the same, only instruction selection and threading differ.
- WHIR parameters are upstream's recommended ones, unmodified (including proof-of-work grinding).
- `prove` returns per-phase timings (`ProveOutput::phases`): decode_key, prepare_key, import_witness, spartan_whir_prove, encode_proof.

## Predicate layer

```text
 Predicate (claim.rs)  --statement()-->  Statement (statement.rs: circuit name, public inputs, witness slots)
        |                                      |  lowering per family: predicate/{mod,arithmetic}.rs
   holds() (semantics.rs, exact.rs)        Predicates (engine.rs): bundled circuit + keys per circuit, cached
   unbounded-integer reference             prove / verify through the same Zk facade and backend
```

- A claim is plain data. `Predicate::statement()` lowers it deterministically to one of the bundled circuits (`sum4`/`sum8`/`arith`/`compare`/... per 32/64/128-bit width) and its public inputs; there are no per-combination circuits. Circuits compose the shared gadgets in `circuits/lib` (limbs, borrow-chain compare, commitment, `Normalize`, `Operand`).
- Verification derives the public inputs from the trusted claim only. Approved circuits are identified by the SHA-256 of their R1CS (`approved.rs`, generated by `scripts/build_circuits.py`, rebuilt and compared byte for byte in the full gate).
- `holds()` is the reference semantics on unbounded integers. The engine uses it to refuse false claims with a clear message, and `differential.rs` uses it as the oracle that every circuit's witness must agree with. It is not a security boundary.
- Each circuit is set up at the policy's security target. A circuit whose size upstream cannot support at that target fails unless the caller explicitly authorizes a lower floor (`Predicates::with_minimum_bits`); it then runs at the highest level upstream attains, not below the floor (`Predicates::security_bits`). A level is never lowered silently and never raised.

## Backend swapping

Implement `zk_core::Backend`. Proof artifacts record their backend id and version and are only accepted by a matching implementation.

`zk-witness` is generic over a `Field` trait (KoalaBear built in), so the same solver serves other fields. `zk-groth16` implements it for BN254 and proves the BN254 predicate builds against snarkjs zkeys with its own Groth16 prover and verifier on arkworks curves (`qap.rs` reproduces snarkjs's extra public-input rows and odd-coset quotient; the matrices come from the r1cs). ark-groth16 is not used because its dependency tree fails `cargo audit`; the zkey header is cross-checked against the r1cs and every circuit against its recorded SHA-256. No keys are stored: `zk_groth16::Ceremony` (`ceremony/`) checks a published phase-1 file by hash, derives each circuit's starting key (byte-identical to snarkjs), adds and verifies contributions, and a `zk_groth16::Setup` accepts a key pack only after verifying every key, and accepts proofs only under the setup or key ids the verifier trusts. Circuits load at run time (a `Directory` natively, a `Memory` filled by the browser worker's fetches); `predicate/trusted_setup.rs` locates the circuits and phase 1. The `Predicates` facade routes a claim to it when the claim's commitments are Groth16 commitments (`predicate/groth16.rs`); set and issuer trees are hashed per scheme (`hash::Node`), so a Groth16 claim never mixes with a Spartan-WHIR root; circuit signals are carried as BN254 scalars, which hold every KoalaBear value, and converted back for Spartan-WHIR. Groth16 predicate proofs are tagged `ZKG16v01` so they are never parsed as Spartan-WHIR artifacts. It is not behind `zk_core::Backend`, which models the six-operation facade's compile/setup flow.
